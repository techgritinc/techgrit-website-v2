Reference Source: `raw-files-v3/TechGrit Website V2.3/TechGrit Data AI.dc.html`. Inspect the reference HTML and the existing Next.js implementation/reusable components before creating anything new; prefer existing `components/ui` components over one-off markup; only create a new reusable component when nothing existing fits. Follow the exact folder/file architecture already established for AI-Accelerated Modernization and Software Product Engineering (page files, section/component organization, supporting components, data/content organization, imports, styling, routing) — do not introduce a different architecture. Use Tailwind CSS only; reuse existing `tokens.css`/`globals.css` tokens, only adding a new one when the reference genuinely requires a value that doesn't already exist; do not move page-specific styling into global styles. The reference HTML is the pixel-accurate visual source of truth — typography, spacing, containers, grids, buttons, radii, borders, shadows, backgrounds, icons, images, responsive behavior, and section ordering must match as closely as technically possible, without arbitrary micro-tuning. The page must be fully responsive (mobile/tablet/laptop/desktop) using the project's existing breakpoints, reproducing the reference's own responsive behavior rather than uniformly scaling the desktop layout. No layout shift, flicker, hydration mismatch, or unnecessary client-side rendering. Keep the implementation minimal: no unnecessary dependencies, duplicate components, wrapper elements, CSS, state, client components, or changes to unrelated pages/components/tokens. Preserve the reference's content and section structure exactly — same section order, headings, supporting text, CTA structure, and links; do not invent replacement content when the reference already provides it, and preserve intentional reference quirks (e.g., a URL without content) rather than inventing a fix."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Evaluate the data & AI engineering offering end-to-end (Priority: P1)

A prospective client (a data leader, CTO, or founder evaluating whether to invest in data/AI capability) lands on the Data & AI Engineering page — from site navigation, the homepage, or a direct link — and reads through the hero promise, the six core capabilities, and the five-stage delivery journey, to decide whether TechGrit's data-and-AI approach fits their needs before requesting contact.

**Why this priority**: This is the entire reason the page exists — it is TechGrit's primary sales asset for the data & AI engineering service line. Without this flow working, the page delivers no value regardless of what else is built.

**Independent Test**: Load the page standalone and verify a reader can, without leaving the page, understand what "data & AI engineering" means at TechGrit, see the six named capabilities (Strategy, Platforms, AI/ML, Agents, Governance, Enable) with their supporting bullet points, and see the five-stage journey (Discover, Build, Enable, Govern, Optimize) — this alone constitutes a usable, demonstrable page.

**Acceptance Scenarios**:

1. **Given** a visitor arrives on the page, **When** the hero section renders, **Then** they see the "Service 03 · Data & AI" eyebrow, the headline "Transform data into intelligence & agentic action." (with "intelligence & agentic action." rendered as the gradient-accented phrase), the supporting paragraph, both hero CTAs ("Schedule an AI Readiness Assessment", "See capabilities"), and the right-side highlight card showing only the replacement image (`svc-qa.png`) with the "AI IMPACT™ · OrbitAI™ · PRISM™ frameworks" caption line beneath it — with the reference's original four stat tiles (Pipelines, Agents, Governance, Time to value) not rendered as text/tiles anywhere on or around the card (per FR-004).
2. **Given** a visitor scrolls past the hero, **When** they reach the "AI is only as effective as the data behind it" intro section, **Then** they see the section's heading and paragraph on one side and the "Where AI programs stall" chip list (six blocker chips) on the other.
3. **Given** a visitor reaches the "Capabilities" section, **When** it renders, **Then** they see the section heading "Six capabilities. One AI-first engine." (corrected from the reference's "Five," per Clarifications) followed by exactly six capability cards (Data Strategy & AI Readiness, Data Platforms & Engineering, AI & Machine Learning Engineering, Agentic AI & Workflow Automation, Analytics/Governance & Responsible AI, Enablement & Adoption), each with its numbered/disciplined label ("01 · Strategy" through "06 · Enable"), heading, lead paragraph, and bullet list, otherwise matching the reference verbatim.
4. **Given** a visitor reaches the "Discover. Build. Enable. Govern. Optimize." section, **When** it renders, **Then** they see the five ordered stages (Discover, Build, Enable, Govern, Optimize) each with its number, title, and description.

---

### User Story 2 - Understand why the approach matters and see relevant industry fit (Priority: P2)

A visitor who is already sold on the need for data/AI help but is evaluating *why TechGrit specifically* reads the "Why AI-first data engineering" tiles and the "Industries we empower" cards to confirm TechGrit understands the data-quality/governance risk angle and has relevant domain experience (HealthTech, FinTech, Construction Tech) before proceeding further.

**Why this priority**: This section builds the trust and differentiation needed to convert an already-interested visitor, but the page is still functional and valuable without a reader reaching this far (P1 covers the core pitch).

**Independent Test**: With only the hero, intro, capabilities, and lifecycle sections present, add the "Why" tiles and "Industries" cards and verify each renders independently with correct content and links, without depending on any interactive state from earlier sections.

**Acceptance Scenarios**:

1. **Given** a visitor reaches the "Why AI-first data engineering" section, **When** it renders, **Then** they see all six tiles (Improve data quality, Accelerate AI adoption, Enable intelligent automation, Better decisions, Scale responsibly, Framework-backed) with icon, heading, and description.
2. **Given** a visitor reaches the "Industries we empower" section, **When** it renders, **Then** they see three linked industry cards (HealthTech, FinTech, Construction Tech) each navigating to that industry's page.

---

### User Story 3 - Resolve open questions and convert (Priority: P3)

A visitor with specific procedural concerns (Data vs. AI Engineering scope, integrating AI into existing products, custom agents, responsible-AI practices, supported cloud/data platforms) expands the FAQ accordion to get direct answers, optionally checks related services, and then acts on a CTA (schedules an AI readiness assessment or books a discovery sprint) or navigates to a related service page.

**Why this priority**: This closes remaining objections and drives the conversion action, but is only reached by visitors who have already engaged with P1/P2 content — it is the funnel's final step, not its entry point.

**Independent Test**: Render just the FAQ, related-services, and closing CTA sections and verify each FAQ item expands/collapses independently, related-service links are correct, and both CTA buttons point to their respective destinations.

**Acceptance Scenarios**:

1. **Given** the FAQ section is visible, **When** a visitor clicks a closed question, **Then** that question's answer expands in place (the first question, "What's the difference between Data Engineering and AI Engineering?", is expanded by default) without affecting the state of other questions.
2. **Given** the "Related services" section, **When** it renders, **Then** it shows six linked service cards (AI-Accelerated Modernization, Software Product Engineering, Platform Engineering, Managed Services, AI Strategy & Roadmap, Startups).
3. **Given** the closing CTA band, **When** it renders, **Then** it shows the heading "Whether it's a data platform, embedded AI, or agentic workflows — we've shipped it.", the supporting paragraph, and both the primary ("Schedule an AI Readiness Assessment") and secondary ("Book a Discovery Sprint") actions.

---

### Edge Cases

- What happens on narrow viewports (mobile) where the hero's two-column layout, the three/six-across capability, why, and industry grids, and the five-across lifecycle strip cannot fit side by side? Each must collapse to a readable single- or two-column stack rather than overflowing horizontally or shrinking text below a legible size.
- What happens when a visitor navigates directly to `#capabilities` (the "See capabilities" hero link) via a bookmarked or shared URL? The target section must be reachable and not obscured by the sticky site header.
- What happens if a visitor expands multiple FAQ items in sequence? Each item's expand/collapse state must be independent of the others (no accordion-style forced-collapse of previously opened items).
- What happens in the "Industries we empower" grid, which the reference lays out on a four-column track while supplying only three cards? The layout must not visibly break or leave an awkward gap that reads as a missing/broken card — it must render the way the reference itself renders it (three cards, trailing space) at every breakpoint, matching the identical treatment already established by the sibling "What We Do" pages' own Industries sections.
- What happens with the "Capabilities" section's heading, which literally reads "Five capabilities. One AI-first engine." in the reference while six capability cards render beneath it? Per Clarifications, this is treated as a content bug in the reference rather than an intentional quirk: the heading is corrected to "Six capabilities. One AI-first engine." so the copy matches the six cards that actually render.
- What happens to the four hero stat tiles and the hero card's decorative treatment once the right-side content is replaced with an image, per FR-004? The card's size, position, border radius, and framing must remain visually equivalent to the reference even though its contents changed from stat tiles to an image plus caption, and the image must not distort or crop awkwardly at any supported viewport width.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The page MUST present all page copy — headings, eyebrows, paragraphs, card titles, bullet lists, FAQ questions/answers, CTA labels, and link labels — exactly as written in the reference prototype, with no rewriting, rephrasing, shortening, expanding, reordering, or added/removed content, except for the single numeral correction in the "Capabilities" section heading described in FR-003 and Clarifications ("Five" → "Six").
- **FR-002**: The page MUST reuse the site's existing shared Header and Footer components without modification or duplication of either component's code, and MUST reuse existing `components/ui/` primitives — `Hero`, `ContentBlock`, `GlassCard` (`serviceCapability` variant), `ProcessSteps`, `Faq`, `IconTile` (for the related-services compact cards), and `final-cta` — wherever their shape already matches this page's sections, in place of building new one-off equivalents.
- **FR-003**: The page MUST render, in reference order: hero, "AI is only as effective as the data behind it" intro/blockers block, six-capability "Capabilities" grid (heading corrected to "Six capabilities. One AI-first engine.", per Clarifications), five-stage "Discover. Build. Enable. Govern. Optimize." lifecycle strip, six-tile "Why AI-first data engineering" grid, three-card "Industries we empower" grid, five-item FAQ accordion, six-card "Related services" grid, and closing CTA band.
- **FR-004**: The hero section's right-side highlight card MUST display only a static image (`public/samples/svc-qa.png`) with the "AI IMPACT™ · OrbitAI™ · PRISM™ frameworks" caption line beneath it — with no rendering of the reference's four stat tiles (Pipelines, Agents, Governance, Time to value) as text/tiles anywhere on or around the card — and without distorting the image's aspect ratio at any supported viewport width, matching the sibling AI-Accelerated Modernization and Software Product Engineering pages' own hero-card image-replacement treatment (chrome, dimensions, position, border radius, spacing) via the shared `Hero` component's `media`/`mediaCaption` slots (per Clarifications).
- **FR-005**: Every interactive affordance present in the reference MUST work in the implementation: each FAQ item independently expands/collapses (first item expanded by default); the "See capabilities" hero link scrolls to the capabilities section without that section being hidden under the sticky header; all CTA, card, and related-service links navigate to their intended destination (or a page-appropriate equivalent where the destination does not yet exist as a built route).
- **FR-006**: The page's visual presentation (typography scale, weight, line-height, letter-spacing, colors, gradients, spacing, card/section dimensions, border radii, shadows, and icons) MUST match the reference prototype at the reference's desktop width, with no visually approximated values where the reference specifies an exact one.
- **FR-007**: The page's layout MUST adapt responsively across desktop, laptop, tablet, and mobile widths, using the project's existing canonical breakpoints (`lg`=1140px, `md`=960px, `sm`=560px) to reproduce the reference's own breakpoint behavior (e.g., multi-column grids collapsing to fewer columns, then to a single column; the hero's two-column split stacking on narrow viewports) rather than a uniform shrink of the desktop layout or a newly invented pixel breakpoint.
- **FR-008**: This phase MUST implement static content only — no network requests, data fetching, CMS integration, or client-side data-derived state — while remaining structured (page-local `_data/types.ts` content shape, matching the sibling pages' own initial-build data organization) so that content can later be supplied dynamically without a rebuild of the page's visual structure, consistent with how both sibling "What We Do" pages were themselves first built before any CMS integration followed later as separate, dedicated work (per Assumptions).
- **FR-009**: No functional requirement in this specification requires modifying any page, component, or configuration outside what is needed to build this new page and the minimal navigation-pointer updates in FR-010.
- **FR-010**: The site's existing "What We Do → Data & AI Engineering" entry points MUST resolve to the new page at the route `/what-we-do/data-ai-engineering` once built. Concretely: (a) the footer's "What We Do" link config (`cms/api/footer.ts`) MUST have its "Data & AI Engineering" entry's `href` updated from `/services#svc-data-ai` to `/what-we-do/data-ai-engineering`; and (b) the header's mega-menu mapping (`cms/api/header.ts`'s `toMegaGroup`), which already special-cases the "AI-Accelerated Modernization" and "Software Product Engineering" entries to override their stale CMS-supplied links, MUST gain an equivalent third special-case for the "Data and AI Engineering" entry pointing to the same new route — following the exact precedent already established in that file. Live CMS content, the rest of the `/services` page, and all other navigation entries remain untouched.
- **FR-011**: This feature MUST NOT introduce any new shared `components/ui/` primitive. Every section this page needs (hero with its image-media treatment, intro/blockers content block, capability card, numbered process step, icon/text tile, FAQ accordion, and closing CTA band) already has a matching, unmodified `components/ui/` component established by the sibling "What We Do" pages; the "Why AI-first data engineering" tiles are implemented as a page-local composition rather than the shared `IconTile`, matching the exact precedent both sibling pages already set for their own equivalent "why" sections. This page's own build work is limited to page-local composition (route-scoped section components under `app/what-we-do/data-ai-engineering/_components/`) that supplies this page's content and copy to those existing primitives.

### Key Entities

- **Capability**: One of the six service offerings shown in "Capabilities" — has a discipline label/number, a title, a short lead description, and a list of supporting bullet points.
- **Lifecycle Stage**: One of the five ordered stages in "Discover. Build. Enable. Govern. Optimize." — has a sequence number, a title, and a description.
- **Value Proposition Tile**: One of the six items in "Why AI-first data engineering" — has an icon, a heading, and a description.
- **Industry Card**: One of the three items in "Industries we empower" — has an icon, a name, a description, and a link to that industry's page.
- **FAQ Item**: One of the five question/answer pairs — has a question, an answer, and an independent expanded/collapsed state.
- **Related Service Link**: One of the six items in "Related services" — has an icon, a name, a short description, and a link to that service's page.
- **Hero Stat Tile**: One of the four stat tiles originally shown in the hero's right-side card (Pipelines, Agents, Governance, Time to value) — retained as the source content that the replacement hero image (`svc-qa.png`) visually represents, matching both sibling pages' equivalent treatment (per Clarifications).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A person familiar with the reference prototype, shown the implemented page side by side with the reference at the same viewport width, cannot identify a visually noticeable difference in any of the nine sections.
- **SC-002**: All page text matches the reference prototype at 100% fidelity — zero content substitutions, omissions, or additions when diffed against the reference's copy — except for the single "Five" → "Six" numeral correction in the Capabilities heading (per Clarifications).
- **SC-003**: The page remains fully readable and free of horizontal overflow or overlapping elements at desktop, laptop, tablet, and mobile widths.
- **SC-004**: A visitor can independently expand each of the 5 FAQ items and reach every one of the 6 capability cards, 5 lifecycle stages, 6 "why" tiles, 3 industry cards, and 6 related-service links without encountering a broken or dead interaction.
- **SC-005**: Both site-wide navigation entry points for this service ("What We Do" footer link and header mega-menu entry) resolve to the new page rather than the old `/services` anchor.

## Assumptions

- The reference prototype (`TechGrit Data AI.dc.html`) is the third of the seven "What We Do" sibling design prototypes already present in `raw-files-v3/TechGrit Website V2.3/` (per its own "Service 03 · Data & AI" hero eyebrow). It reuses the exact hero, content-block, capability-card, process-step, icon-tile, FAQ, and CTA-band markup structure the sibling AI-Accelerated Modernization and Software Product Engineering pages already extracted into `components/ui/` (`Hero`, `ContentBlock`, `GlassCard`, `ProcessSteps`, `Faq`, `IconTile`, `final-cta`), differing only in copy, stat values, and section counts. This is the basis for FR-011: no new shared primitive is needed for this page.
- **Static content only, CMS integration deferred** (confirmed via Clarifications): Both sibling "What We Do" pages have, as of this writing, since received their own separate CMS-integration follow-up work (fetching content from a live Strapi endpoint via `cms/api/what-we-do/*.ts`). This spec targets the sibling pages' own *initial* build phase instead — a static local TypeScript content module (`_data/types.ts` + a page-local content constant), not a live CMS integration — consistent with how every "What We Do" page in this codebase was first built statically before any CMS integration followed later as its own separate, dedicated ticket (per FR-008).
- **Hero card image-replacement treatment** (confirmed via Clarifications): Both sibling pages replaced their hero card's stat-tile content with a static image. This page follows the same treatment. Unlike those siblings — where an orphaned asset's filename directly matched the service (e.g. `svc-eng.png` for "Software Product Engineering") — no remaining unused asset in `public/samples/` thematically fits "Data & AI Engineering"; of the two remaining unused `svc-*` assets (`svc-qa.png`, `svc-uiux.png`), `svc-qa.png` was chosen as the first candidate in that same naming bucket (per Clarifications). Unlike the Software Product Engineering page (which dropped its card's caption line entirely, per its own explicit clarification), this page retains the caption line ("AI IMPACT™ · OrbitAI™ · PRISM™ frameworks") beneath the image, matching the AI-Accelerated Modernization page's equivalent card, which also kept a caption — the more conservative default given this ticket's own emphasis on not dropping reference content without an explicit reason to.
- The "Why AI-first data engineering" tile pattern is implemented as a page-local composition (not the shared `components/ui/IconTile`), matching the precedent already set by both sibling pages' own equivalent "why" sections, which made the same architectural choice for the same visual pattern.
- The "Industries we empower" section reuses `GlassCard`'s `serviceCapability` variant on a four-column desktop track supplying only three cards, matching the sibling pages' identical treatment of their own equivalent Industries sections.
- The "Capabilities" section heading's numeral is corrected from the reference's literal "Five capabilities. One AI-first engine." to "Six capabilities. One AI-first engine." (confirmed via Clarifications), since six capability cards render beneath it and the mismatch reads as a content bug in the reference rather than an intentional quirk — unlike the Industries 4-column/3-card layout treatment below, which is a genuine, intentionally preserved layout quirk rather than a copy error.
- Destination links to sibling "What We Do" / Industries pages referenced by this page (e.g., AI-Accelerated Modernization, Software Product Engineering, HealthTech, FinTech, Construction) point to those pages' intended routes regardless of whether each sibling page has been built yet; this page's own build does not block on their existence.
- "Pixel-perfect" is evaluated at the reference's authored desktop viewport; intermediate breakpoints follow the reference's documented responsive rules mapped onto this codebase's existing canonical breakpoints (`lg`=1140px, `md`=960px, `sm`=560px) rather than the reference's own literal inline breakpoints (1080px/920px/640px), per established project convention.
- Legal/placeholder footer links (Privacy Policy, Terms of Service, Cookie Preferences) inherit whatever the existing shared Footer already does site-wide; this feature does not alter Footer behavior.
- The new page lives at `/what-we-do/data-ai-engineering` (`app/what-we-do/data-ai-engineering/page.tsx`), following the exact routing and file/folder pattern already established by `app/what-we-do/ai-modernization/` and `app/what-we-do/software-product-engineering/`. Today, both the footer's "What We Do" list and the header's live CMS-driven mega menu point this service at `/services#svc-data-ai`, an anchor inside the combined Services page; FR-010 repoints both to the new route, mirroring the precedent already set for the AI-Accelerated Modernization and Software Product Engineering entries in both files.
