## Clarifications

### Session 2026-08-26

- Q: This ticket key (`TMS-67`) is already used by the existing `specs/TMS-67` directory (Construction Industry Page) and `specs/TMS-67-healthcare` (Healthcare Industry Page). Should this feature reuse either directory, or get its own? → A: A separate directory, `specs/TMS-67-fintech`, same disambiguation pattern already used for `TMS-67-healthcare`, `TMS-65-leadership-advisory`, `TMS-85-tokens-v2-migration`.
- Q: What is the page's actual content source and section list? → A: A CMS endpoint (`GET /api/pages/by-slug/fintech`) returning 7 ordered sections: Hero, "What We Build", a product-lifecycle section, an engineering-services section, "FinTech Solutions We Support", "Featured Case Studies", and a closing CTA banner. Per explicit instruction, the Healthcare-equivalent "Connected Systems" section is excluded — and the CMS payload doesn't return one for this page anyway, so no section is being dropped from the live data.
- Q: FinTech's sections are structurally identical to Healthcare's — how do we avoid a third copy-paste of the same components (Construction, then Healthcare, now FinTech)? → A: Extract the shared shapes into `components/ui/` (not a new Industries-only folder) — this repo's existing pattern for a section shape reused across a route family (`Hero`, `ContentBlock`, `ProcessSteps`, `IconTile`, `GlassCard`, all already in `components/ui/` and reused by `what-we-do/*`/`how-we-work/*`). Scope is Healthcare + FinTech only — Construction is explicitly out of scope for this feature. This feature (1) generalizes Healthcare's `whatWeBuild`/`productLifecycle`/`engineeringServices`/`solutionsWeSupport` section components into shared, prop-driven `components/ui/` components — checking whether the existing `Hero.tsx`/`GlassCard.tsx` already cover a shape before adding a new file — and updates Healthcare's page to consume them (behavior-preserving, no visual change), and (2) extracts the matching CMS-mapping helpers (mirroring `cms/shared/reusable-sections.ts`) so `cms/api/healthcare.ts` and the new `cms/api/fintech.ts` share mapper functions instead of each declaring near-identical ones. FinTech's "Featured Case Studies" section keeps its own mapper/component (CMS shape differs from Healthcare's equivalent).
- Q: FinTech's "What We Build" section supplies a section-level subtitle paragraph that Healthcare's equivalent shared component has no slot for — render it or drop it to match Healthcare's exact shape? → A: Add an optional description slot to the shared "What We Build" component (rendered only when present, same pattern the shared product-lifecycle component already uses); no change to Healthcare's render since its own subtitle is empty.
- Q: Re-verified against the live CMS (`GET /api/pages/by-slug/fintech`, re-fetched during clarification — the ticket's original pasted payload was stale): "Featured Case Studies" is now `industries-construction.proven-impact` (identical component type to Healthcare's "Featured Capabilities"), and its 2 cards now carry a real `ctaLabel`/`ctaLink` ("Read case study" → `/insights/case-studies/`). Should this section still get its own FinTech-only mapper/component, and should the case-study link still be omitted? → A: No to both. Since the CMS shape is now identical to Healthcare's, this section reuses the same shared mapper AND the same shared `components/ui/` component as Healthcare's "Featured Capabilities" — no FinTech-specific code for this section at all. The "Read case study" link now renders (the earlier "omit the case-study link" requirement was based on stale data); the metric/label fields remain empty for both pages' cards, so no metric number renders, unchanged.
- Q: Once Healthcare's `whatWeBuild`/`productLifecycle`/`engineeringServices`/`solutionsWeSupport` section components are generalized into shared `components/ui/` components (per the extraction above), what happens to Healthcare's original route-local `_components/healthcare-*.tsx` files for those four shapes? → A: Delete them once the shared versions exist and Healthcare's page is updated to consume them — no deprecated/unused files left behind. Consistent with this repo's standing rule against half-migrated leftovers; leaving them in place would also contradict SC-008's "zero net-new near-duplicate components" goal.
- Q: The CMS payload's own section titles for the product-lifecycle and engineering-services sections are copy-pasted from Healthcare — literally "AI Across the **Healthcare** Product Lifecycle" and "Our **HealthTech** Engineering Services" — inside an otherwise fully FinTech-worded payload (subtitle, all card copy). Render the CMS titles literally, or correct them? → A: Correct them to FinTech-appropriate wording ("AI Across the FinTech Product Lifecycle" and "Our FinTech Engineering Services") — this is an evident CMS authoring/copy-paste bug, not an intentional value, consistent with the precedent set in `specs/TMS-86-data-and-ai-engineering` (correcting "Five capabilities" to "Six capabilities" for the same reason: rendering an evident content bug literally would visibly mislabel the page).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Evaluate TechGrit's FinTech offering (Priority: P1)

A FinTech decision-maker (bank digital-product lead, payments startup founder, wealth-management platform CTO) lands on the FinTech industry page — from the Industries mega-menu, a search result, or a shared link — to quickly understand whether TechGrit builds the kind of financial software their organization needs, and how to start a conversation.

**Why this priority**: This is the entire purpose of the page. Every other behavior (responsive layout, visual fidelity, section content) exists in service of this one evaluation-and-conversion journey. Without it, the page delivers no value.

**Independent Test**: Load `/industries/fintech` on desktop, tablet, and mobile widths and confirm a visitor can read a clear FinTech-specific value proposition in the hero, scroll through all seven sections without any broken or missing content, and reach a working "talk to us" call-to-action at the bottom of the page.

**Acceptance Scenarios**:

1. **Given** a visitor arrives at the FinTech page, **When** the hero section renders, **Then** they see an "Industry · FinTech" eyebrow badge, a headline with "FinTech Companies" highlighted, a supporting description, exactly one primary CTA button ("Talk to Our Engineering Team"), and a fixed-size picture area on the right that does not resize based on content — with no breadcrumb trail and no statistics/metrics overlay anywhere in the hero, matching the Healthcare hero's structure exactly.
2. **Given** a visitor scrolls past the hero, **When** they reach the "What We Build" section, **Then** they see an intro paragraph beneath the section title, followed by 8 FinTech-specific cards (Digital Payments & Embedded Finance, Wealth & Investment Platforms, Lending & Credit Platforms, Crypto Asset & Digital Wallet Solutions, Trading & Capital Markets Platforms, Personal Finance & Payroll Solutions, Regulatory Compliance & Risk Management, Financial Analytics & Business Intelligence), each with an icon, title, and description, rendered by the same shared card-grid component Healthcare's "What We Build" uses (extended with an optional description slot for the intro paragraph).
3. **Given** a visitor continues scrolling, **When** they reach "AI Across the FinTech Product Lifecycle", **Then** they see 6 FinTech-AI cards (AI-Powered Financial Assistants, Fraud Detection & Risk Intelligence, Intelligent Document Processing, Predictive Analytics, Workflow Automation, Knowledge Intelligence), each with a numbered step label (`1`–`6`), title, and description, rendered by the same shared component Healthcare's product-lifecycle section uses.
4. **Given** a visitor reaches "Our FinTech Engineering Services", **When** the section renders, **Then** they see 7 rows (Strategy & Design, Software Product Engineering, AI-Assisted Modernization, Platform Engineering, Data & AI Engineering, Quality Engineering, Managed Services) with title and description — this page's CMS payload supplies no icon for any of the 7 steps, so every row's icon slot renders empty (no icon, no substitute label) using the exact same no-fallback rule Healthcare's own icon-less step already follows, uniformly.
5. **Given** a visitor reaches "FinTech Solutions We Support", **When** the section renders, **Then** they see an eyebrow ("We Support"), a title, and all 18 solution names (Digital Payments, Payment Orchestration, Banking-as-a-Service (BaaS), Embedded Finance, Digital Wallets, Crypto Asset & Wealth Management, Lending & Credit Platforms, Investment & Portfolio Management, Algorithmic Trading, Treasury Management, Revenue Cycle & Billing Platforms, Personal Finance Applications, Savings & Payroll Automation, AI-Powered Advisory Tools, Fraud Detection & Risk Management, Regulatory Compliance & AML, Financial Reporting & Analytics, Insurance Technology Platforms) as title-only tiles (no icon, no description) in a grid that shows 3 columns on desktop and above, 2 columns on tablet, and a single stacked column on mobile — the same shared tile-grid component Healthcare's "Solutions We Support" section uses.
6. **Given** a visitor reaches "Featured Case Studies", **When** the section renders, **Then** they see 2 cards (Multi-Provider Payment Integration for a Field Service SaaS Platform, Commodity Trading Platform Development) with title, description, and a "Read case study" link (to `/insights/case-studies/`), using the exact same shared component and mapper as Healthcare's "Featured Capabilities" section (same CMS component type, `industries-construction.proven-impact`) — no metric number renders, since neither page's cards supply one.
7. **Given** a visitor reaches the bottom of the page, **When** the closing CTA section renders, **Then** it uses the same shared CTA component (`components/ui/final-cta`) already used by the Healthcare and Construction pages' closing CTAs, populated with this page's own heading ("Build the Future of Financial Technology"), description, and primary CTA ("Talk to Our Engineering Team").
8. **Given** the same visitor resizes their browser or opens the page on a phone, **When** the layout crosses the project's existing breakpoints, **Then** every section reflows the same way its referenced Healthcare/Construction section does at the same widths, with no arbitrary new breakpoints.

### Edge Cases

- What happens if the hero image asset is missing? The fixed-size picture area must still render at its intended dimensions (no collapse or layout shift) with a defensive placeholder, matching the shared hero component's existing behavior.
- What happens if a card's description text is unusually long, or a "FinTech Solutions We Support" title is unusually long for its dense tile? Cards/tiles must wrap text rather than overflow, matching the shared components' existing behavior.
- What happens for "Our FinTech Engineering Services" where every one of the 7 steps has a `null` CMS icon? Every row renders with no icon slot, cleanly — the shared component MUST NOT substitute a placeholder, assigned icon, or the CMS's own `stepLabel` value as a fallback (this is the same no-fallback rule Healthcare's equivalent section already follows for its one icon-less step, now exercised for all 7 steps instead of 1 — kept uniform rather than special-cased, since Healthcare's spec explicitly ruled out fallback logic "going forward").
- What happens if "Featured Case Studies" cards render without an icon (the CMS payload supplies none)? The layout must not leave a broken image or misaligned gap — the icon slot is omitted cleanly.
- What happens if a visitor tabs through the page with a keyboard? All interactive elements (hero CTA, closing CTA) must remain focusable and operable, consistent with existing site-wide keyboard behavior.
- What happens on the exact breakpoint boundaries (`lg`/`md`/`sm`)? The page must reflow at the same three canonical breakpoints already established site-wide, not new ones introduced for this page.
- What happens to the Healthcare page's own rendered output once its section components are generalized into shared components? It MUST be visually and behaviorally unchanged — the extraction is a behavior-preserving refactor, verified by comparing Healthcare's rendered page before and after.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The page MUST be reachable at a URL under the Industries section, following the same routing convention as the existing Construction/Healthcare pages (`/industries/fintech`).
- **FR-002**: The page MUST reuse the Industries family's established file-and-folder architecture (route-local `page.tsx` inside `app/industries/fintech/`) and MUST consume shared, prop-driven section components rather than duplicating Healthcare's route-local components a third time.
- **FR-003**: This feature MUST extract the Healthcare section components whose shape FinTech also needs (hero, "What We Build" card-grid, numbered product-lifecycle card-grid, numbered/icon engineering-services rows, title-only solutions tile-grid) into shared, prop-driven `components/ui/` components — reusing the existing `Hero.tsx`/`GlassCard.tsx` where they already cover the shape, adding a new `components/ui/` file only where they don't — and MUST update the Healthcare page to consume them without changing Healthcare's rendered output, deleting Healthcare's now-unused original route-local components for those shapes rather than leaving them in place. Construction is out of scope for this extraction.
- **FR-004**: This feature MUST extract the corresponding CMS-mapping helper functions (mirroring the existing `cms/shared/reusable-sections.ts` pattern) so that `cms/api/healthcare.ts` and the new `cms/api/fintech.ts` both call shared mapper functions for the section shapes they have in common, instead of each declaring near-identical per-file mapper functions.
- **FR-005**: The page's content MUST be sourced from the CMS `by-slug/fintech` page payload's ordered `sections` array, defensively rendering `null`/missing content the same way Healthcare and Construction do, rather than hardcoded copy.
- **FR-006**: The hero section MUST present, on its left side: an "Industry · FinTech" eyebrow badge, a headline with the phrase "FinTech Companies" highlighted, a supporting description, and exactly one primary call-to-action button ("Talk to Our Engineering Team") — with no breadcrumb trail — using the shared hero component from FR-003.
- **FR-007**: The hero section's right side MUST present a picture area of fixed dimensions that does not grow or shrink based on content, and MUST NOT include any statistics/metrics overlay.
- **FR-008**: The page MUST NOT include an integrations-strip section, a lifecycle-diagram (SVG node/connector) section, or a Connected Systems section.
- **FR-009**: The page MUST include a "What We Build" section presenting its CMS-supplied intro paragraph and 8 cards (icon, title, description), using the shared card-grid component from FR-003, extended with an optional section-level description slot.
- **FR-010**: The page MUST include an "AI Across the FinTech Product Lifecycle" section (CMS title corrected per Clarifications) presenting its 6 CMS-supplied cards (numbered step label `1`–`6`, title, description — the CMS-supplied icon for this section is not rendered), using the shared numbered card-grid component from FR-003.
- **FR-011**: The page MUST include an "Our FinTech Engineering Services" section (CMS title corrected per Clarifications) presenting its 7 CMS-supplied steps (step label `01`–`07`, title, description), using the shared component from FR-003; since this page's CMS payload supplies no icon for any of the 7 steps, every card's icon slot MUST be omitted cleanly rather than substituting a fallback/placeholder icon.
- **FR-012**: The page MUST include a "FinTech Solutions We Support" section presenting an eyebrow ("We Support"), a title, and its 18 CMS-supplied plain-title items (no icon, no description) as tiles in a grid that shows 3 columns on desktop and above, 2 columns on tablet, and 1 column on mobile, using the shared tile-grid component from FR-003.
- **FR-013**: The page MUST include a "Featured Case Studies" section presenting its 2 CMS-supplied cards (title, description, case-study link), reusing the exact same shared mapper and `components/ui/` component as Healthcare's "Featured Capabilities" section (both are `industries-construction.proven-impact`) — no FinTech-specific code for this section.
- **FR-014**: The page's closing call-to-action section MUST use the same shared CTA component (`components/ui/final-cta`) already used by the Construction and Healthcare pages' closing CTAs, populated with this page's own CMS-supplied heading, description, and primary CTA label/link.
- **FR-015**: The page MUST be fully responsive across desktop, tablet, and mobile, reflowing at the project's existing canonical breakpoints (no new arbitrary breakpoints).
- **FR-016**: The page MUST reuse existing shared components (`components/ui/*`, the shared closing-CTA component, the existing "Proven Impact" pattern for "Featured Case Studies", existing icon set) wherever they already cover a needed UI element — this feature introduces no FinTech-only components.
- **FR-017**: The page MUST reuse existing design tokens (`app/tokens.css`, `app/globals.css`) for all colors, spacing, typography, radii, and shadows, adding a new token only when a CMS-driven value has no existing equivalent.
- **FR-018**: The initial render MUST NOT visibly flicker, shift layout, or show an intermediate incorrect state as the page hydrates.
- **FR-019**: No section's icon field MUST be assigned a substitute/placeholder icon when the CMS leaves it `null` — every card's icon renders only when the CMS supplies one, and is cleanly omitted otherwise. (This applies to icons specifically; it does not change the hero's existing defensive image placeholder.)

### Key Entities

- **FinTech Page Section**: A named, ordered section of the page as returned by the CMS (hero, "What We Build", "AI Across the FinTech Product Lifecycle", "Our FinTech Engineering Services", "FinTech Solutions We Support", "Featured Case Studies", closing CTA), each with the content fields it needs to render.
- **Approach Step / Card**: A single item within "What We Build", "AI Across the FinTech Product Lifecycle", "Our FinTech Engineering Services", or "Featured Case Studies" — carries a title, an optional description, an optional step label, and an optional icon.
- **Solution Tile**: A single plain-title item within "FinTech Solutions We Support" — carries only a title (no icon, no description).
- **Shared Section Component**: A generalized, prop-driven `components/ui/` component (hero, card-grid, numbered card-grid, engineering-services rows, tile-grid) consumed by both the Healthcare and FinTech pages instead of each maintaining its own near-identical copy.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A visitor can identify TechGrit's FinTech value proposition and locate a working call-to-action within the first screen of the page, without scrolling, on a standard desktop viewport.
- **SC-002**: The page renders with no visible layout shift or flash of incorrectly-sized content during initial load, on both desktop and mobile.
- **SC-003**: At the project's three canonical breakpoints, each section's layout matches the same reflow behavior already verified on the Healthcare/Construction pages it shares components with — confirmed by side-by-side comparison at each breakpoint.
- **SC-004**: 100% of the page's visual styling (color, spacing, radius, typography) traces back to an existing or newly-added token — zero hardcoded hex/px/rgba literals duplicating an existing token.
- **SC-005**: The hero's picture area maintains its fixed footprint regardless of viewport width or content length (verified at desktop, tablet, and mobile widths).
- **SC-006**: All 7 CMS sections render their full content (every card/tile present in the `by-slug/fintech` payload) with no items silently dropped.
- **SC-007**: After the shared-component extraction, the Healthcare page's rendered output (all 8 of its sections) is visually and behaviorally unchanged from before this feature — verified by side-by-side comparison of `/industries/healthcare` pre- and post-refactor.
- **SC-008**: Zero net-new near-duplicate section components are added anywhere on the page — all 6 section shapes (hero, What We Build, product lifecycle, engineering services, solutions tiles, featured case studies) reuse an existing or newly-shared `components/ui/` component, each consumed by both Healthcare and FinTech.

## Assumptions

- The CMS `by-slug/fintech` payload (7 ordered sections) is the authoritative content and structure source for this page.
- The page follows the same CMS-content-shape pattern already used by Construction and Healthcare (typed section content resolved through `cms/api`, defensively rendering `null`/missing content), consistent with how every other Industries-family page in this repo is built.
- Per explicit clarification, this feature performs a behavior-preserving refactor of Healthcare's existing section components into shared, prop-driven `components/ui/` components rather than duplicating them a third time for FinTech — matching the repo's existing pattern for section shapes reused across a route family (`Hero`, `ContentBlock`, `ProcessSteps`, `IconTile`). Construction is explicitly untouched by this feature.
- The two CMS section titles copy-pasted from Healthcare ("AI Across the Healthcare Product Lifecycle", "Our HealthTech Engineering Services") are corrected to FinTech wording in the rendered page only (CMS source data unchanged), consistent with the "Five" → "Six capabilities" precedent in `specs/TMS-86-data-and-ai-engineering`.
- "Featured Case Studies" reuses Healthcare's existing "Featured Capabilities" mapper and component as-is, verified against the live CMS to be the same component type (`industries-construction.proven-impact`) with matching fields, including a populated case-study link.
- The shared closing-CTA component (`components/ui/final-cta`) is reused as-is, matching the Construction and Healthcare pages' existing usage.
- No contract/fixture file of the captured CMS payload is kept in this feature's spec directory — the CMS endpoint itself is the live source of truth, matching the Healthcare spec's own precedent.
